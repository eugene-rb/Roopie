## 2. 非アクティブ時の透過

### 切り分け

自前のコードは無罪だった。

- `browser.js:636` の `window.on('focus')` はキーボードフォーカスを移すだけで外観に触らない
- レンダラーにフォーカス依存のスタイルは無い（`:focus-within` はアドレスバーの枠のみ）

症状は「フレームも含めてウィンドウ全体が単色」。ユーザーの追加報告では
「うっすら透過されている気もするが明らかに別物」——これは、DWMが描く単色フォールバックの上に
クローム側のCSSの半透明（`windowTranslucency` 62%）が乗るため。探りでは中身を全面透過にしたので
素の単色グレー（`mean=[84,84,84]`）として出た。

### 実測（`scripts/test-window-focus-material.js`）

判定は目視ではなく数値。背後に**幅120px**の縞を敷き、画素のばらつき `sd` と
隣接画素差 `edge` から「単色 / くっきり素通し / ぼけて透過」を3分する。
縞を細くするとacrylicのぼかし（半径30px前後）で潰れて単色と区別が付かなくなるため幅を取った。

| 条件 | 結果 |
| --- | --- |
| acrylic / アクティブ | 透過（sd=56.5） |
| acrylic / 非アクティブ | **単色**（sd=0） |
| mica・tabbed / 非アクティブ | **単色**。代替にならない |
| 非アクティブのまま押し直す | 戻る。ただし**5秒以内にまた単色へ落ちる** |
| 押し方（同値 / `none`を挟む / 同tick） | **差なし**。どれも戻るし、どれも落ちる |
| 1秒間隔で押し続ける | 透過を維持（＝採用） |
| 押し続けたときの残差 | 約300ms刻み40回で**1〜3回だけ単色を掴む**。間隔を変えても減らない |

「押し直しの瞬間に一瞬フォールバックが見えているのでは」という筋は**否定された**。
12秒あたりの押す回数が 12/6/5 回になる 1000/2000/2500ms で、単色フレームは 1/3/1 回と
ばらつくだけで押す回数と相関しない。先に取った「500ms間隔で20回中1回」も n=20 のノイズの範囲。
間隔を延ばす根拠が無いので、減衰（3〜5秒で落ちる）への余裕が最大の 1000ms を採る。
ただし**数%のフレームが単色になる残差は消せていない**。目視で脈打って見えるなら、
間隔ではなく別の押し方（ネイティブの `SetWindowCompositionAttribute` 等）を検討することになる。

### Decisions

- **「非アクティブの間だけ押し直し続ける」形にする**（`syncMaterialKeepAlive()`）。
  一発の再適用では数秒で落ちるので `blur` ハンドラだけでは直らない
- **押し方は「同じ値をもう一度渡す」**。`none` を挟む形も同じだけ効くが、手数が少ないほうを採った
  （当初は「`none` を挟むと一瞬フォールバックが見えるのでは」と考えたが、後の測定でその筋は否定された）
- **最小化中は押すのを休む**（タイマーは残す）。見えていないものにDWM呼び出しを撃たない
- **`applyWindowChrome()` からも見直しをかける**。テーマを切り替えた相手が
  非アクティブなウィンドウのことがあり、そのときは `blur` が飛ばない
- **マテリアルの決定を `browser.windowMaterial(ctx)` に切り出した**。押し直し側と
  `applyWindowChrome` で判定がずれると、シークレットにacrylicを撃つような事故になる
- **ネイティブモジュール（`SetWindowCompositionAttribute`）は採らなかった**。
  フォーカス非依存で本筋ではあるが、castLabs ECS へのリビルドとVMP再署名が要る
  （`CLAUDE.md` の配布ビルド要件）。1秒のタイマーで実測上足りているので割に合わない

## 探りを作るときに踏んだ罠（次に測る人向け）

- **`alwaysOnTop` を外すと測定が壊れる**。他アプリのウィンドウが撮影範囲に被り、
  2回続けて全数値が使い物にならなかった。「最前面だとDWMが活性扱いするのでは」という
  懸念は、**ケース2（非アクティブ・押し直しなし）が単色に戻ること**を見張りにして潰せる
- **`execFileSync` は既定で `windowsHide:false`**。撮影のたびにコンソール窓が一瞬前面に出る。
  最初はこれを減衰の犯人と疑ったが、隠しても減衰したので無罪（ただし探りには入れてある）
- **フォーカスの奪い合いが決着する前に撮ると壊れる**。`win.isFocused()` が期待値になるまで
  リトライする `settle()` を入れた。入れる前は「非アクティブのはずが focused=true」が出た

## 残っている確認事項

- **実機目視（未実施）**: liquidglass / 半透明にして他アプリをクリックし、
  透過が保つこと。**脈打って見えないか**は特に見てほしい。探りでは押し続けても
  数%のフレームが単色を掴んでおり、目のほうが速い可能性がある
- **`start:verify`（実質未実施）**: 起動はしたが「キャッシュを移動できません（アクセス拒否）」が出ており、
  ユーザーの Roopie が起動中＝単一インスタンスロックで即死していた疑いが濃い。
  通ったのは `node --check`（構文）だけで、`syncMaterialKeepAlive()` は一度も走っていない。落としてから回すこと
- **探りは素の `BrowserWindow` でしか測っていない**。実機のウィンドウには
  `transparent: true` の内部ページViewが乗っており、[[2026-08-06_glassmorphism-transparency]] が
  「合成の経路が違うので実測が要った」と書いた通り、そこは別経路。1秒ごとの押し直しが
  Viewを再描画させないかは未測定。**設定（内部ページ）を開いた状態**と通常のWebページで
  見比べれば、ちらつきがDWM側かView側かを切り分けられる
- 非アクティブのウィンドウを何時間も放置したときの1秒タイマーの妥当性。
  最小化中は休むようにしてあるが、「見えているが非アクティブ」のまま放置すると撃ち続ける

## Risks

- DWMの挙動はWindowsの更新で変わりうる。変わったら**まず探りを回す**（数値で出る）
- `syncMaterialKeepAlive()` は `ctx.materialTimer` をウィンドウのコンテキストに生やしている。
  ウィンドウを破棄する経路を増やすときは `closed` で止まることを確認する
